# Апаратні нотатки: FP32 vs FP16 на RTX 2050 (EfficientNet-B0, крок навчання)

Дата вимірювань: 2026-11-21. Усі числа — з реальних запусків, сирі логи поруч у `results/`.

## Конфігурація

| Параметр | Значення |
|---|---|
| GPU | NVIDIA GeForce RTX 2050 (Ampere GA107, compute 8.6, 16 SM, 4 ГБ VRAM), драйвер 581.80, режим WDDM |
| CPU | AMD Ryzen 5 5500H (8 логічних потоків) |
| ПЗ | Windows 11, Python 3.11.9, PyTorch 2.14.1+cu126, cuDNN 9.10.02 |
| Модель | EfficientNet-B0 (torchvision), 17 класів, синтетичний батч 3×224×224 |
| Крок | forward + CE loss + backward + AdamW (GradScaler для AMP) |
| `cudnn.benchmark` | **True** для всіх режимів (як у `train.py`) |
| TF32 за замовчуванням у цій збірці | `cudnn.allow_tf32=True`, `cuda.matmul.allow_tf32=False` |
| TF32 у бенчмарку | задано явно для кожного режиму (див. таблиці) |
| Методика | нова модель на кожен запуск; 10 кроків прогріву (включно з автотюнінгом cuDNN), 20 вимірюваних; 3 повтори; режими чергуються по колу; у таблицях — медіана |

Скрипти: [`scripts/bench_precision.py`](../scripts/bench_precision.py), [`scripts/profile_precision.py`](../scripts/profile_precision.py).

## 1. Перевірка «13×» (batch 64, як у навчанні)

Лог: `bench_precision_benchmark1.txt` / `.json`.

| Режим | cudnn.allow_tf32 | matmul.allow_tf32 | img/s (медіана; min–max) | мс/крок | Пікова пам'ять, МБ |
|---|---|---|---|---|---|
| FP32 | False | False | **15.9** (15.9–17.9) | 4028 | **5493** |
| FP32 | True | True | 15.7 (15.4–17.0) | 4075 | 5493 |
| AMP FP16 | False | False | **239.6** (239.6–239.9) | 267 | 2854 |

**Прискорення FP16/FP32 = ×15.1.** Отже, різниця на порядок підтвердилася: раніше швидкий тест дав 13×, у цьому акуратнішому вимірюванні вийшло ×15.

Ключова деталь: пікова пам'ять у FP32 становить **5493 МБ, а фізичної VRAM лише 4096 МБ.**

## 2. Той самий тест, коли FP32 вміщується у VRAM

Логи: `bench_precision_bs32.txt`, `bench_precision_bs16.txt`.

| Batch | FP32 TF32 off, img/s | FP32 TF32 on, img/s | AMP FP16, img/s | FP16 / FP32 | Пам'ять FP32 / FP16, МБ |
|---|---|---|---|---|---|
| 64 | 15.9 | 15.7 | 239.6 | **×15.1** | 5493 / 2854 |
| 32 | 120.1 | 125.9 | 232.1 | **×1.93** | 2809 / 1471 |
| 16 | 116.3 | 122.5 | 201.6 | **×1.73** | 1447 / 779 |

Щойно FP32 вміщується у 4 ГБ, він стає у 7.5 раза швидшим: 15.9 img/s при batch 64 проти 120.1 при batch 32. Перевага FP16 при цьому зменшується до ~1.7–1.9×. TF32 дає лише +5%.

## 3. Профілювання (batch 32, TF32 off): де саме виграє FP16

Лог: `profile_precision.txt`.

**Пошарово.** Кожен із 81 Conv2d мережі виміряно окремо (forward+backward) з реальною формою входу:

| Тип згортки | К-сть | FP32, мс | FP16, мс | FP32/FP16 | Частка часу згорток у FP32 |
|---|---|---|---|---|---|
| depthwise k×k | 16 | 70.8 | 63.3 | **×1.1** | 42% |
| pointwise 1×1 | 64 | 91.4 | 48.8 | **×1.9** | 55% |
| звичайна k×k (stem) | 1 | 5.1 | 5.4 | ×0.9 | 3% |
| усі Conv2d | 81 | 167.2 | 117.5 | ×1.4 | — |

**Повний крок навчання (`torch.profiler`).** Сумарний час CUDA-ядер становить 268.9 мс у FP32 проти 130.7 мс у FP16 (**×2.06**). Найбільші статті витрат в обох режимах:
- поелементні ядра: активація SiLU, множення в Squeeze-Excitation, бінарні операції;
- backward BatchNorm;
- копіювання Device→Device;
- depthwise-ядра PyTorch (`at::native::conv_depthwise2d_*`).

## Висновок: причина 13–15×

1. **Головна причина: нестача відеопам'яті, а не FP32-арифметика.** У FP32 при batch 64 активації для backward займають ~5.5 ГБ, що більше за 4 ГБ VRAM. У режимі WDDM драйвер NVIDIA не видає помилку out-of-memory. Натомість він переносить частину даних у системну RAM ("System Memory Fallback", shared GPU memory), і GPU звертається до неї через PCIe. Це на порядок повільніше за GDDR6, тож крок займає ~4 с замість ~0.27 с. AMP FP16 удвічі зменшує розмір активацій (2.85 ГБ) і вміщується у VRAM. Звідси й «магічні» 15×. Підтвердження: при batch 32/16 (FP32 вміщується) різниця падає до 1.7–1.9×.

2. **Гіпотеза «повільні depthwise conv у FP32» не підтвердилася.**
   - Depthwise-згортки однаково повільні в обох точностях (×1.1): вони виконуються власними ядрами PyTorch, без Tensor Cores, і впираються в пропускну здатність пам'яті, а не в обчислення.
   - Справжній ×2 у межах VRAM дають дві речі. По-перше, pointwise 1×1 згортки (по суті матричне множення): у FP16 вони йдуть на Tensor Cores (×1.9). По-друге, поелементні операції та BatchNorm, де FP16 удвічі зменшує кількість байтів, які треба прочитати й записати.
   - Для порівняння, крок 1 (`check_env.py`): чисте множення матриць 4096×4096 дало 4.15 TFLOPS у FP32 проти 12.42 у FP16 (×3).

3. **Висновок для архітектури.** На GPU з 4 ГБ VRAM вирішальним ресурсом є обсяг і пропускна здатність пам'яті, а не пікові FLOPS. AMP тут потрібен не лише для швидкості. Він дозволяє лишитися в межах фізичної VRAM при batch 64.

## Обмеження та невирішене

- Рядок «FP32 + TF32 on» при batch 64 так само впирається в переповнення пам'яті, тому TF32 там нічого не показує.
- Значення `max_memory_allocated` більше за 4096 МБ — непряма ознака підкачки. Лічильник shared GPU memory у Диспетчері задач Windows окремо не знімали.
- Сповільнення `channels_last` з AMP при batch 64 (16 img/s проти 248, помічене під час кроку 3) окремо не досліджено. Пояснення через depthwise-ядра в форматі NHWC або через пам'ять наразі лише припущення.
- Вимірювання на ноутбуці від мережі. Частоти GPU плавають; нагрів не контролювався, окрім чергування режимів.
